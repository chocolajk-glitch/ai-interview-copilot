# 动机卡 03 · Redis

## 第 1 层（概念）
- **是什么**：基于内存的**数据结构服务器**（不是单纯的 KV）
- **解决什么问题**：磁盘数据库（MySQL）太慢，需要"亚毫秒级"的中间层；memcached 太弱（纯 KV）

## 第 2 层（实现）
- **核心数据结构**（不是单纯的 string）：
  - **String**：基础 KV、计数器、分布式锁
  - **Hash**：对象字段存储
  - **List**：消息队列、最新列表
  - **Set / Sorted Set**：排行榜、共同好友
  - **Stream**：持久化消息流（Kafka-like）
  - **Bitmap / HyperLogLog / Geospatial**：特殊结构
- **单线程**（6.0 之前）——靠**IO 多路复用 epoll** 扛高并发
- **内存存储** + 异步持久化（RDB 快照 / AOF 日志）
- **RESP 协议**：自定义的文本协议，客户端和服务端通信

## 第 3 层（动机）
- **时代背景**：2009 年，磁盘数据库时代（MySQL 统治）
  - 一次 query 10-50ms
  - 缓存要么用 memcached（**纯 KV，没有数据结构**）
  - 要做排行榜、共同好友这种"带计算的查询"——MySQL 死慢，memcached 算不了
- **作者痛点**（Salvatore Sanfilippo）：
  - 想给一个意大利创业公司做"实时排行榜 + 反垃圾邮件"
  - memcached 太弱（只 KV，没法做 ZSET）
  - MySQL 太慢（每次 update ranking 全表锁）
- **设计选择**：
  - **内存为主**——牺牲持久性换速度（**用户场景决定**：缓存丢了重算可以）
  - **数据结构丰富**——不只是 KV，是"**带计算能力的内存数据结构**"——直接 `ZADD` `ZREVRANGE` 出排行榜
  - **单线程 + epoll**——避免锁，简化实现，性能靠 IO 多路复用
  - **RESP 协议**——简单文本协议，**可读、可手写、跨语言**

## 一句话设计哲学
> **"不只是 KV，是带计算能力的内存数据结构"**——把"缓存 + 排行榜 + 计数器 + 消息队列"统一在一份内存里。

## 面试话术示例
"Redis 不只是内存 KV，是**带原子操作的内存数据结构服务器**。ZSET 排序、List 队列、Stream 持久化消息——都能在服务端算好再返回。**解决了我之前用 memcached 存排行榜时，要把全榜拉回客户端排序的痛点**。**代价是单线程 + 内存贵，大 key 会阻塞整个实例**。"
