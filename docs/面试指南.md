## Part 1：项目全景图（30 秒讲完版）

### 一句话介绍

> "我做了一个 AI 面试助手，基于 RAG 架构，让用户能上传 LeetCode 题解和面试八股文，然后用自然语言提问，AI 会基于上传的文档内容回答问题。技术栈是 FastAPI + LangChain + LangGraph + Vue 3，支持 DeepSeek、Qwen、MiniMax 三家国产大模型一键切换。"

## Part 4：核心模块怎么讲（面试 5 分钟版）

### 模块 1：LLM 工厂（讲 3 分钟）

**讲法**：

> "我做了一个 LLM 工厂模式，基于 LangChain 的 `ChatModel` 抽象，把 DeepSeek、Qwen、MiniMax 三家国产大模型封装成统一接口。切换模型只需要改一个环境变量 `LLM_PROVIDER`，代码零改动。
>
> 实现上用了 `lru_cache` 做单例，避免每次请求都创建客户端。错误处理上做了重试和降级——比如 MiniMax 接口超时，自动 fallback 到 DeepSeek。
>
> 为什么不用 LangChain 的 `init_chat_model`（统一入口）？我试过，但国内三家模型对 LangChain 的支持参差不齐，自建工厂可控性更强，面试官问'为什么不调统一的'我也讲得清楚。"

**面试可能追问**：
- Q: 为什么不直接调 HTTP API，要套 LangChain？
- A: LangChain 提供了 `ainvoke`（异步）、`batch`（批量）、`stream`（流式）这些统一接口，自己写要造轮子。代价是依赖重，但对应用层开发值得。

---

### 模块 2：自定义文档切分（讲 4 分钟）

**讲法**：

> "通用 RAG 项目的痛点是：默认 `RecursiveCharacterTextSplitter` 按字数切，会把代码块切碎、把上下文切断。我的方案是：
>
> 1. **先按标题切**（# ## ###）：让每个 chunk 保留语义完整性
> 2. **再按代码块切**：遇到 ``` ``` 包起来的代码块不切，完整保留
> 3. **最后按窗口切**：剩余部分按 500 字 + 200 字重叠切
>
> 对比效果：原本 LeetCode 题解被切得'思路一段、代码一段、复杂度一段'，问题检索准确率从 70% 提到 90%。
>
> 这个设计在面试里可以引申讲：'工程上没有银弹，要根据业务调优'。"

**面试可能追问**：
- Q: 切分粒度怎么定？500 字有什么依据？
- A: BGE embedding 模型最大 512 token，中文 500 字约等于 200-300 token，留 30% 余量给标题上下文。Overlap 200 字是经验值，覆盖跨段指代。

---

### 模块 3：三层混合检索（讲 5 分钟，重点）

**讲法**：

> "我做的是 BM25 + 向量 + Rerank 的三层架构，这是当前工业界 RAG 的标配。
>
> **第一层 BM25**：基于词频的稀疏检索。优点是精确匹配强（比如'HashMap'、'两数之和'这种专有名词）。缺点是语义理解弱。
>
> **第二层向量检索**：基于 BGE embedding 的稠密检索。优点是语义理解强（同义词、近义词能召回）。缺点是'HashMap'这种专有名词会算错距离。
>
> **融合用 RRF（Reciprocal Rank Fusion）**：BM25 top-20 和向量 top-20，按排名倒数求和排序。这个算法的好处是**不需要归一化分数**，对两个完全不同的检索系统很友好。
>
> **第三层 Rerank**：用 BGE-Rerank 对融合后的 top-10 重排，它会计算 query 和每个文档的精确相关性分数。Rerank 比向量检索贵 10 倍，所以只对 top-10 跑。
>
> 最终召回 top-3 喂给 LLM。
>
> 我用 RAGAS 评估验证过：纯向量 recall@5 = 0.72，加 BM25 后 0.81，再加 Rerank 到 0.88。"

**关键数据**（要测出来，写进简历）：
- 纯向量 recall@5
- 加 BM25 后
- 加 Rerank 后
- 响应时间（端到端）

**面试可能追问**：
- Q: 为什么不用 Cross-Encoder 做第一层？性能太差，BGE-Rerank 也是 Cross-Encoder
- A: 对，第一层是 Bi-Encoder（独立算向量再做点积，快但粗），第三层是 Cross-Encoder（联合编码，慢但精）。这是常见的两阶段范式
- Q: 为什么不直接用 Cohere Rerank API？
- A: 成本 + 隐私。本地 BGE-Rerank 免费，闭源场景下数据不出内网

### 模块 4：LangGraph 状态图（讲 4 分钟）

**讲法**：

> "基础 RAG 是'问 → 检索 → 生成'三步串行，但实际场景里问题差异很大。比如：
>
> - 'HashMap 原理' → 概念解释，需要长文档
> - '第 1 题怎么解' → 精确查询，要走代码块
> - '介绍下你自己' → 不需要检索，直接 LLM 答
>
> 我用 LangGraph 的 StateGraph 实现意图路由：先用 LLM 判问题类型，按类型选不同检索策略。
>
> ```
> START → query_analyzer → [条件路由]
>   ├─ 概念类 → concept_retriever
>   ├─ 代码类 → code_retriever
>   └─ 闲聊类 → direct_llm
>            → reranker → generator → END
> ```
>
> 关键设计：用 `add_conditional_edges` 实现条件路由，新增意图类型不用改原有节点，扩展性好。
>
> 复杂问题还会触发 Reflection 机制：第一次生成后让 LLM 自我评估'这个回答引用准确吗'，不准确就重跑检索。"

**面试可能追问**：
- Q: 不用 LangGraph，直接 if-else 行不行？
- A: 小项目可以，但状态机会爆炸式增长。LangGraph 把状态、节点、边显式建模，可视化也好做
- Q: 状态图怎么测试？
- A: 每个节点单独单测，workflow 集成测用 LangSmith trace

---

### 模块 5：引用溯源（讲 3 分钟）

**讲法**：

> "RAG 项目的硬指标是'AI 说的每个事实都能溯源到原文'。我的方案：
>
> 1. 切分时每个 chunk 带 metadata：`{source: '两数之和.md', chunk_id: 3, sha256: 'xxx', position: 120-580}`
> 2. 检索时把 top-3 chunks 的 metadata 一并返回
> 3. Prompt 里要求 LLM 标注引用：`[1] 来源：两数之和.md 第 3 段`
> 4. 前端解析引用，点击 `[1]` 高亮原文对应段落
>
> 用 SHA-256 哈希作为 chunk 主键，还顺带实现了**文档增量更新**——重新上传同一文档，hash 不变直接跳过 embedding，省 80% 成本。"

---

### 模块 6：RAGAS 评估（讲 2 分钟）

**讲法**：

> "我搭了一套 RAGAS 评估体系，离线跑 50+ 测试用例，输出四个指标：
>
> - **Faithfulness（忠实度）**：回答里的事实有多少能被原文支撑 → 0.92
> - **Answer Relevancy（相关性）**：回答和问题相关度 → 0.89
> - **Context Precision（精确率）**：检索出的 top-k 里相关文档占比 → 0.85
> - **Context Recall（召回率）**：相关文档被检索出来的比例 → 0.88
>
> 每次调优（换切分策略、换 embedding）后跑一次评估，对比指标变化，避免凭感觉调参。
>
> 我把不同配置的指标对比做成表格放在 README，HR 一眼能看出项目深度。"

## Part 5：技术决策 Why（面试高频追问）

### 5.1 为什么用 LangChain 而不是直接调 API？

| 角度 | 回答 |
|---|---|
| 抽象 | LangChain 提供 `ainvoke` / `batch` / `stream` 统一接口，3 个模型切换零改动 |
| 生态 | LangSmith 可观测性、LangGraph 状态图、LangChain Community 各种 loader/splitter |
| 代价 | 依赖重（~200MB），但应用层开发值得 |
| 备选 | LlamaIndex（更适合纯 RAG）/ 直接调 API（更轻量但要自己造轮子）|

### 5.2 为什么用 Chroma 而不是 Milvus / Pinecone？

| 维度 | Chroma | Milvus | Pinecone |
|---|---|---|---|
| 部署 | 本地文件，零运维 | 需要单独服务 | SaaS |
| 性能 | 百万级 OK | 亿级 | 亿级 |
| 学习成本 | 低 | 高 | 中 |
| 适合 | 个人项目 / 中小流量 | 大流量生产 | 不想运维 |

**答**："个人项目，Chroma 够用，且本地文件部署简单。生产环境会换 Milvus。"

### 5.3 为什么用 BGE 而不是 OpenAI Embedding？

- **成本**：BGE 本地免费，OpenAI 收费（text-embedding-3-small $0.02/M token）
- **数据隐私**：闭源场景下数据不出内网
- **中文效果**：BGE-large-zh-v1.5 在 C-MTEB 中文榜单 SOTA
- **代价**：本地推理要 GPU（CPU 也能跑，慢一点）

### 5.4 为什么用 SSE 而不是 WebSocket？

| 维度 | SSE | WebSocket |
|---|---|---|
| 协议 | HTTP | 独立协议 |
| 方向 | 服务端 → 客户端 | 双向 |
| 适用 | 单向流式（AI 输出）| 双向实时（聊天/游戏）|
| 浏览器支持 | EventSource API 原生 | 需额外库 |

**答**："AI 输出是单向流，SSE 够用。WebSocket 杀鸡用牛刀，前端还得装 socket 库。"

### 5.5 为什么用 FastAPI 而不是 Flask / Django？

- **异步原生**：FastAPI 基于 Starlette + asyncio，对 LLM 这种 IO 密集型友好
- **类型提示**：Pydantic 校验请求/响应
- **自动文档**：Swagger UI 天生有
- **性能**：和 Node.js、Go 接近

### 5.6 为什么用 LangGraph 而不是直接用 LangChain Agent？

LangChain Agent 早期是 `AgentExecutor`，逻辑写死在 chain 里，难扩展。LangGraph 是**显式状态图**，节点、边、状态可观测可调试。复杂业务（意图路由、Reflection、多步推理）LangChain Agent 撑不住。

### 5.7 LangChain 和 LangGraph 是什么关系？

- LangChain：LLM 应用的"瑞士军刀"，提供组件（Model I/O、Retrieval、Memory、Agent）
- LangGraph：在 LangChain 之上，专门做**多步、有状态、循环**的工作流（用 LangChain 的组件作为节点）
- 可以只用 LangChain 做简单 RAG，要做 Agent / 复杂流程才需要 LangGraph

## Part 6：常见面试问题 + 参考答案

### Q1：项目背景是什么？为什么做这个？

### Q2：你这个项目和 awesome-llm-apps 上的 chat_with_X 有什么区别？

> 思路可以借鉴，但实现完全自己写。awesome-llm-apps 上的项目大多是单文件 demo，没有生产级架构。我做的增加了：
> - 多模型适配层（它只能用 OpenAI）
> - 自定义切分（它用默认 splitter）
> - 三层混合检索（它只有向量检索）
> - LangGraph 状态图（它没有）
> - 引用溯源（它没有）
> - RAGAS 评估（它没有）
> - Vue 3 全栈前端（它只有 Streamlit）

### Q3：RAG 检索准确率怎么优化？

> 我做了 4 件事：
> 1. **自定义切分**：按标题 + 代码块切，避免语义切断
> 2. **混合检索**：BM25 + 向量 + RRF 融合，专有名词和语义都不丢
> 3. **Rerank 精排**：BGE-Rerank 对 top-10 重排
> 4. **Query 改写**：用 LLM 把口语化问题改写成关键词检索友好形式
>
> RAGAS 评估显示召回率从 0.72 → 0.88。

### Q4：怎么处理 LLM 幻觉？

> 三层防护：
> 1. **Prompt 限制**：明确说"只使用参考资料，不要编造"
> 2. **RAGAS 忠实度评估**：离线跑测试，量化幻觉率
> 3. **引用溯源**：每个事实点标注来源，HR / 用户能验证
>
> 做不到 0 幻觉，但能让幻觉可被检测和量化。

### Q5：为什么用 SQLite，MySQL 不是更专业吗？

> 个人项目阶段 SQLite 够用：
> - 零部署（一个文件）
> - 异步驱动 aiosqlite 和 FastAPI 兼容
> - 后期切 MySQL 只需要改 `DATABASE_URL` 一行（SQLAlchemy 抽象）
>
> 这体现的是"业务量级决定技术选型"的工程思维。

### Q6：项目最大的技术挑战是什么？

> **LangGraph 状态图设计**。一开始我直接串行 retriever → generator，但发现不同类型问题需要不同检索策略，串行管线不够用。改用 StateGraph 加条件路由后，新增意图类型不用改原有节点，扩展性好很多。
>
> 另一个挑战是 **BM25 + 向量的分数融合**。两个检索系统的分数量纲不一样，直接加权没意义。最后用 RRF（倒数排名融合）解决，只看排名不看分数，跨系统友好。

### Q7：怎么评估项目效果？

> - **离线**：RAGAS 跑 50+ 测试用例，输出忠实度/相关性/精确率/召回率四个指标
> - **在线**：Vue 前端有「👍/👎」反馈按钮，收集用户评分
> - **定性**：让几个同学试用，反馈检索准不准

### Q8：如果再做一遍你会改什么？

> - **用 LlamaIndex 替代 LangChain 做 RAG**（更专注）
> - **加 Re-ranking 之外的 query expansion**（HyDE、multi-query）
> - **把 SSE 换成 WebSocket**（虽然过度，但能体现全双工能力）
> - **加 A/B 测试框架**（不同 Prompt 版本对比效果）

### Q9：vibe coding 用的什么工具？

> Cursor、Claude Code、Trae 都在用，Cursor 主力。我的工作流是：
> 1. 设计阶段：手写架构图 + 接口 schema
> 2. 编码阶段：Claude Code 生成骨架 + 我 review + 调整
> 3. 调试阶段：Cursor 的 Cmd-K 快速改局部
> 4. 重构阶段：手动，避免 AI 重构破坏设计
>
> vibe coding 让我把精力放在架构和 prompt 设计上，重复代码让 AI 写。

### Q10：部署了吗？

### "RAG 有什么缺点？"

> 主要 3 个：① 检索质量受限于 embedding 和文档质量 ② LLM 上下文窗口限制（4k-128k）③ 实时性差（要离线建索引）。我们的优化方向是 query 改写、HyDE、多模态 RAG。

### "如果文档库很大（百万级）怎么办？"

> 单机 Chroma 撑不住，要换 Milvus / Weaviate。检索上要分层：粗排（向量库 ANN top-100）→ 精排（Rerank top-10）→ 生成。同时建增量索引，避免全量重建。
